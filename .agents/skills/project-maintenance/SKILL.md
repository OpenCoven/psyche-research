# Project maintenance

Read root AGENTS.md, docs/STATUS.md and docs/DECISIONS.md. Run `python3 .agents/skills/project-maintenance/scripts/audit.py --output var/agent-maintenance/latest.json` from the repository root. This collects metadata only; it does not run application commands, read ignored data, fetch branches, publish or delete anything. Exit 2 means remote evidence is incomplete; read the receipt and use the connected GitHub REST fetch tool to obtain missing endpoints. Never replace failed reads with a claim that there are no issues/checks.

Read the live epic #1, relevant issue bodies and latest comments before choosing work. Compare their acceptance evidence with the current branch, not a neighboring candidate. Keep implemented, tested, integrated, hosted and human-accepted states distinct. Refresh all pages of issues and PRs, the actual head checks and the PR stack. The script returns all issue/PR pages, current-main checks, and checks for every open PR head; its latest 30 workflow runs are a bounded history sample, not a complete run inventory.

At every session start inspect local ownership and outstanding checks. Run the full remote audit once per active day, after a head/ownership change, and before publication or cleanup. During the weekly review also invoke `$worktree-prune`, review Dependabot changes against DECISIONS (especially the Django 5.2 LTS decision), and identify stalled blockers, missing owners and duplicate work. A clean tree, old timestamp or terminal CI result does not release an owner's work.

Planning issue/label maintenance is authorized by root instructions. Preserve existing assignments and labels; reconcile only evidence-backed status, dependencies and bounded next actions. Do not close acceptance issues merely because implementation exists. Do not invent GitHub Project Status from issue state or titles: discover the actual linked board and its supported REST fields first. If Projects or milestone/label endpoints are unavailable, record that limit and retain explicit issue-body planning fields. Use REST (`gh api` or the connected REST fetch path); no implicit GraphQL fallback.

Use the connector's additive issue-label operation for priority/status/area labels and verify the resulting issue. This repository's supported additive write successfully created missing labels even though repository-label collection reads were rejected; do not infer that an unavailable collection endpoint blocks every relevant operation. Derive priorities from the current issue's explicit planning priority, use deferred/acceptance/blocked labels only with supporting issue evidence, and preserve unrelated labels and owners. `update_issue(labels=...)` replaces the label set, so prefer the additive operation for reconciliation. Label success does not establish access to native milestones or Project fields.

Reconcile native milestones against the current issue graph, preserving an existing conflicting assignment for owner review. Epic #1 spans all milestones and intentionally has no single milestone. Verify explicit target assignments with fresh issue reads and report newly arrived unmapped issues separately; do not assume a fixed issue count or that every unmapped issue is the epic. Keep due dates unset unless an actual delivery commitment exists.

Separate transport failures from resource permissions. A session-only, certificate-verified REST route using an existing credential restored milestone access when ordinary CLI DNS and connector allowlists failed; the exact local recovery and receipts are recorded in docs/AGENT_READINESS.md. Do not print/store credentials, weaken TLS or change system DNS by inference. Public Projects may be readable without authentication even when a scope-limited credential returns 404; that does not prove private-board absence. Filter Project items to this repository, inspect actual field IDs before interpreting Status, and keep private or unlinked coverage explicitly unknown when access is incomplete.

Before an authorized issue/PR body or comment write, inspect the exact serialized payload. Each prose paragraph must be one logical line, with semantic Markdown blocks preserved. Do not publish private manuscript text, tokens, logs or environment values. Before publishing source, re-read the Vercel project's current Git link and deployment options; verify the automatic deployment path is disabled or resolve the existing manual deployment guard, and obtain applicable source/deployment authority. Historical failed deployments do not prove current trigger behavior, and a disabled Git link does not grant source-delivery approval. A maintenance run does not grant delivery authority.

Report changed facts, exact revision/check links, first failures, remaining unknowns and one highest-priority unblocked action. Update docs/AGENT_READINESS.md when findings materially change. Store raw local receipts only under ignored `var/agent-maintenance/`; public summaries must omit machine paths and sensitive data. The GitHub workflow validates relevant PRs on their exact head and executes this skill's deterministic collector weekly; an agent must still interpret the findings using this skill. A configured schedule is active only after integration on the default branch and a verified scheduled run.
