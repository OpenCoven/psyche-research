# Coven Research verification plan

Status: independent acceptance design, 2026-11-04. These are required checks and evidence definitions, not test results. The project status must separately identify implemented, locally tested, hosted, reviewed, and human-accepted work.

## Evidence contract

For each execution, record the exact revision or dirty-tree identifier, date, operating system, Python/framework/database versions, command, exit status, test count, first failure, retries or skips, artifacts, and remaining limitations. Preserve first-failure evidence even when a later run passes. A command that did not run is unverified. A fixture test, a local browser, CI, and the deployed system answer different questions.

Use clearly named synthetic accounts and manuscripts only in isolated test databases and local previews. Do not put invented contributors, papers, reviews, or endorsements on public pages. Test-only fixtures must not be loaded automatically in deployment or migration.

## Migration and concurrency gates

Start with an empty database, apply all committed migrations, run framework/model checks, and verify no migration drift. Repeat against a database at the previous release containing synthetic private and public records; compare counts, relationships, snapshot digests, access controls, decisions, and withdrawal behavior before and after. Migrations must not create a moderator, public example research, endorsements, credentials, or an open intake setting by accident.

Run the real schema constraints against the supported database. SQLite write contention must be tested with separate connections or processes; a transaction test that shares one connection does not prove concurrent capacity or publication correctness. At minimum, race two final-slot submissions, duplicate publication, revision creation, pause versus submit, and competing correction decisions. Either one succeeds and the other receives a controlled conflict, or both succeed only when the invariant permits it. A raw lock error with no corruption is safer than wrong publication but still needs a usable error/retry path before pilot.

Before changing a deployed schema, take and verify a backup. Test the migration on a copy and record its duration. Prefer backward-compatible additive changes; do not assume a reverse migration restores deleted data. For a failed migration or incompatible application rollback, pause writes and restore a verified backup to an empty target, then explicitly account for writes since backup. Do not run a destructive rollback on the live database merely to prove it is possible.

## Backup and restore drill

1. Create an isolated database with a synthetic contributor and moderator, partial draft, pending submission, private decision note, appeal/report, approved v1, pending correction, approved v2, and withdrawn publication. Store expected public/private visibility and content digests in a local test artifact.
2. Produce a backup while exercising supported writes through the application's documented method. For SQLite, use the online backup API or a quiesced offline process, not an uncoordinated copy of the main file while a WAL may contain accepted writes. Set restrictive output permissions and record source revision, schema version, timestamp, checksum, and backup command result without dumping confidential records into logs.
3. Check database integrity and foreign keys. Restore into a fresh empty path with no serving application connected; refuse accidental overwrite of an existing live target. Verify checksum and reject a deliberately truncated or corrupt copy.
4. Run migrations/checks on the restored copy and repeat authentication, ownership, private search sentinel, immutable snapshot, version history, and withdrawal tests. Compare expected accepted records and digests. Record recovery time and maximum accepted-data loss relative to backup timestamp.
5. Document encrypted off-host transfer, access controls, retention/expiry, and restore credentials as separate operator gates. A local backup round trip does not prove an encrypted off-host copy is available or a disaster recovery target can be reached.

## Delivery and hosted pilot gates

| Gate | Necessary evidence | What it does not prove |
| --- | --- | --- |
| Local product suite | Actual passing commands, test names/counts, failure history, environment, migration/restore results. | Hosted TLS, cookies, proxy body limits, domain, monitoring, legal approval, human usability, or live cost. |
| Independent agent review | Reviewer identity/task, exact reviewed revision or diff, findings, fixes, retest. | Human peer review, independent scientific judgment, penetration testing, or certification. |
| Browser QA | Actually rendered current client, URLs/session, viewport, relevant keyboard/visual observations, errors. | Full assistive-technology or WCAG conformance. |
| CI | Current pushed revision and terminal job results, no unexplained skips. | Delivered production tree or runtime acceptance. |
| Staging rehearsal | Approved non-public environment, exact revision, production settings checks, private intake workflow, rollback and restore rehearsal. | Permission to launch publicly or invite participants. |
| Hosted pilot readiness | Explicit deployment approval, domain/TLS, secrets provisioned by authorized human, durable storage and encrypted backups, rate/proxy checks, observability, named operator schedule, policy approval, accessibility review. | Scientific validation or a guaranteed response schedule. |
| Go/no-go | Human decision recorded against pilot limits, open failures, privacy/security conditions, founder time/cost, and pause criteria. | Authorization for a wider public launch, payments, DOI contract, or external invitations. |

The release record must give each gate one of: verified with linked evidence, failed with first failure, unrun, blocked by a named dependency/permission, or deliberately deferred with product exposure removed. Do not mark the full goal achieved because only local tests pass. Keep safe implementation and planning work moving while approval-dependent external actions remain pending.
